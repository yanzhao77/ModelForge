# ModelForge 下一迭代周期技术开发计划

**版本定位：** `v0.1.2-dev` 后续开发迭代，尚未进入正式 `v0.1.2` 发行候选阶段。
**作者：** Manus AI
**适用范围：** FastAPI/SQLite 运行时与 PySide6 桌面客户端。
**本计划原则：** 桌面端优先、默认不执行、用户范围显式可见、运行记录可追溯、敏感内容不进入新增记录。

## 1. 周期目标与问题定义

本周期的目标不是增加更多独立页面，而是将已经存在的自动化、知识集合、Agent 定义和模型洞察基础实现升级为**可验证、可解释且默认安全的闭环**。目前计划草稿、定义快照、集合归类和聚合指标读取接口已存在，但计划恢复、集合级检索实际约束、指标写入及桌面端多语言仍未完成。[1] 这些缺口若不先收敛，会使后续 Agent 工作台、插件中心和跨平台发行难以获得可信的验证结论。

> **本周期主目标：** 用户能够在桌面端清晰定义“何时可运行、能检索什么、使用了什么定义、产生了哪些非敏感运行指标”，而应用不会因浏览页面、保存草稿或重启而产生意外执行。

| 目标编号 | 技术目标 | 用户可感知结果 | 完成定义 |
|---|---|---|---|
| G1 | 受控自动化可靠性 | 已启用计划在应用恢复后可安全恢复；草稿、暂停和错过的触发不会意外创建 Run。 | 计划状态、下一次执行、并发策略、失败暂停与审计记录一致。 |
| G2 | 知识范围真正生效 | 绑定集合的 Chat/Agent 只检索该用户选择的集合，并能追溯引用来源。 | 检索层而非仅 UI/定义层执行集合成员过滤。 |
| G3 | Agent 定义可审阅 | 用户可查看模板、定义版本、模型目标、工具/审批和知识范围，再显式运行。 | 保存、克隆、恢复和预览均不创建 Run。 |
| G4 | 隐私优先的模型洞察 | 模型完成后只写入用户级聚合桶；洞察页可解释成功率、延迟和估算成本。 | 不保存消息正文、提示词、响应、密钥、完整 URL 或认证头。 |
| G5 | 桌面体验一致性 | 自动化、控制中心和工作台的中英日切换不出现硬编码混合文案。 | 新增字符串均通过本地化键，异步操作不阻塞 Qt 主线程。 |

## 2. 架构决策与范围边界

### 2.1 自动化运行模式的选择

针对本地优先产品的计划执行，本周期保留两个可行方向，并将基础实现限定在不扩大基础设施的前提下。

| 方案 | 运行方式 | 取舍 | 成本 | 配置复杂度 |
|---|---|---|---|---|
| A：本地受控调度 | 桌面/本地运行时启动后恢复**用户已启用**计划；错过的触发默认跳过。 | 与本地优先定位一致，断网时不依赖云端；应用关闭时不承诺后台执行。 | 无新增托管成本。 | 低；复用现有 Scheduler、SQLite 与 Agent Runtime。 |
| B：独立常驻调度服务 | 计划由远程或常驻服务运行，桌面端只管理定义。 | 可提供 24/7 执行，但需要账户、部署、凭据隔离、网络恢复、配额与通知体系。 | 需要长期托管与运维投入。 | 高；超出当前本地单用户范围。 |

本周期仅规划并实施**方案 A** 的安全闭环；方案 B 被记录为未来“可选同步/常驻代理”方向，只有在用户明确要求应用关闭后仍持续执行时才评估。该取舍避免把周期性任务错误地扩展成隐式云端自动化，并保持“显式启用、明确运行、可审计”的现有产品原则。[1]

### 2.2 明确非目标

本周期不引入远程云端 cron、子分钟轮询、Webhook、自动下载模型、自动训练、自动启用计划、真实模型调用演示、公开知识集合、团队多租户共享、自动切换默认模型或正式 Release。跨平台签名、打包和正式 `v0.1.2` 标签继续遵循独立发行门槛。[2]

## 4. 具体开发任务

### 阶段 0：数据一致性与安全基线

首先建立之后所有功能切片共享的可验证边界。当前部分新增实体依赖 `Base.metadata.create_all()` 的兼容性创建，下一步应明确“新库创建”与“既有 SQLite 数据库升级”的路径，并保留不破坏历史 Agent/Run 的迁移策略。

| 编号 | 任务 | 主要代码边界 | 验收标准 |
|---|---|---|---|
| F0-01 | 盘点新增表并补充增量迁移/启动说明。 | `backend/app/models/records.py`、应用启动与迁移文档。 | 旧库升级不会删除用户表、历史 Run、模型配置或知识文档；新库可创建全部新增表。 |
| F0-02 | 统一新增工作区的 user ownership 校验与 404/403 语义。 | `workspaces.py`、`agent.py`、服务层。 | 使用他人 ID 的集合、产物、计划、模板或配置档均不能读取、修改、归类或导出。 |
| F0-03 | 建立可复用的脱敏与导出规则。 | `RedactionService`、产物/日志导出路径。 | API Key、Token、密码、Cookie、Authorization、私钥块和预定义 PII 字段均不出现在产物、错误和指标中。 |
| F0-04 | 统一本地时间显示与 UTC 存储约定。 | 时间 schema、PySide6 格式化辅助函数。 | API 返回可比较 UTC 时间；界面始终显示用户本地时间与时区。 |

### 阶段 1：调度恢复与执行语义

现有 `ScheduleService` 只覆盖 `once` 与 `interval`，并可在显式启用时附接运行时回调；它尚未实现应用启动恢复、每日/每周规则、持久化 `next_run_at` 推进、完整并发策略与错过触发治理。[3] 本阶段将调度定义转化为运行时可恢复但仍默认保守的控制面。

| 编号 | 任务 | 实现要点 | 验收标准 |
|---|---|---|---|
| F1-01 | 扩展计划 schema 与校验。 | 增加 `daily`/`weekly` 简易规则、有效 IANA 时区、`misfire_policy=skip` 与受限并发策略枚举。 | 非法频率、时区、并发值或无 Agent 定义的计划均被服务端拒绝；草稿保持禁用。 |
| F1-02 | 实现确定性的下一次运行计算。 | 纯函数计算 `next_run_at`；一次性计划完成后终止；间隔/日周计划按时区前进。 | UI 可预览下五次触发；夏令时与应用重启不会生成倒退时间。 |
| F1-03 | 在启动生命周期恢复已启用计划。 | 启动时按用户逐一加载 `enabled=true`，注册 callback；过期触发只写可解释的跳过记录或按策略前进，绝不立即补跑。 | 重启后仅原本启用计划恢复；草稿/暂停计划不注册；不会因恢复自动创建历史 Run。 |
| F1-04 | 完成并发、失败与取消状态机。 | `skip`、`queue_one`、`allow_parallel` 的状态与限额；失败计数、自动暂停、取消后清理 runtime job。 | 同一计划的重复触发得到确定结果；达最大失败数后暂停并产生审计事件；删除保留执行审计。 |
| F1-05 | 完善自动化桌面页。 | 计划详情显示时区、下一次五次执行、定义版本、并发/失败策略、关联 Run 与失败原因；所有文案走 i18n。 | 启用、暂停、删除、立即运行均展示名称、影响和确认；刷新页面不触发 Run。 |

### 阶段 2：集合级检索强制约束

当前 Agent 定义能够安全保存并验证 `knowledge_config.collection_ids`，但 Chat/RAG 查询尚未据此过滤。[1] 本阶段将“已保存的范围”提升为实际检索边界，且保证旧会话仍保持全库默认行为。

| 编号 | 任务 | 实现要点 | 验收标准 |
|---|---|---|---|
| F2-01 | 定义统一知识绑定 schema。 | 使用 `all`、`collections`、`disabled`；集合 ID 去重、归属校验、旧配置兼容映射。 | 未绑定/旧会话保持 `all`；`disabled` 不访问知识库；`collections` 必须含至少一个自有集合。 |
| F2-02 | 将集合成员过滤下沉至查询服务。 | 在文档→chunk 查询时使用成员关联过滤，而非桌面端后过滤；保持用户过滤。 | 任一引用的 document/chunk 均属于绑定集合且属于当前用户。 |
| F2-03 | 把绑定接入 Chat 与 Agent runtime。 | 创建/编辑时只保存配置；实际调用时由 runtime 传入 binding；定义版本固定保存选择范围。 | Chat/Agent 只检索许可集合；保存、预览、克隆和版本恢复不执行检索。 |
| F2-04 | 扩充来源追溯 API/UI。 | 回答引用含 collection、document、chunk、分数/排序理由的脱敏摘要；集合删除仅删关联。 | 用户可从回答跳回集合和文档；删除集合不会删除文档本体或跨集合关联。 |
| F2-05 | 增加集合管理桌面工作流。 | 集合列表、成员文档、移除关系、删除集合影响预览、Agent 绑定可视卡片。 | 所有删除/解绑操作有确认；文档可安全属于多个集合。 |

### 阶段 3：Agent 工作台与三语言收敛

本阶段将现有模板和版本 API 组织为桌面上的“定义优先”工作台，同时消除自动化/控制中心中已经识别出的中文硬编码。功能重点是审阅和保存，不是扩大无提示执行范围。

| 编号 | 任务 | 实现要点 | 验收标准 |
|---|---|---|---|
| F3-01 | 建立 `AgentWorkbenchPage`。 | “定义、模板、运行历史”三栏；显示模型目标、工具矩阵、人工审批、输入 schema、知识范围和变更说明。 | 页面展示不创建 Run；明确区分保存草稿、保存版本和显式运行。 |
| F3-02 | 补全模板/版本操作。 | 模板克隆、导入预览、版本对比、恢复为新版本、关联历史 Run 回放。 | 导入忽略凭据/绝对路径/Run ID；恢复不改写历史快照。 |
| F3-03 | 完成自动化与控制中心 i18n。 | 将硬编码窗口标题、提示、错误、空状态、确认文本和列表格式替换为 `zh_CN`/`en_US`/`ja_JP` 键。 | 三种语言切换后无跨语言残留；翻译键缺失有可诊断的开发期提示。 |
| F3-04 | 提供统一的后台加载与错误反馈。 | 页面加载、筛选、导出预览和健康检查均走 `ApiWorker`；维护可恢复错误状态。 | Qt 主线程不因网络 API 阻塞；失败操作保留用户当前选择并给出可重试建议。 |

### 阶段 4：聚合指标写入与模型洞察

`ModelMetricBucket` 当前只有读取聚合路径，洞察页会因缺少写入而为空。[1] 本阶段在模型调用结束的既有路径增加 best-effort 聚合写入，失败不得影响聊天或 Agent 的原结果。

| 编号 | 任务 | 实现要点 | 验收标准 |
|---|---|---|---|
| F4-01 | 建立 `ModelMetricRecorder`。 | 以用户、模型引用、小时/日 bucket 聚合 request、success、4xx/429/5xx/timeout、延迟、token/成本估算。 | 同一调用仅记一次；写入异常被隔离且不改变调用结果。 |
| F4-02 | 接入本地与远程完成路径。 | Chat、OpenAI Responses、Chat Completions、Agent runtime 在结果或异常收尾处提交最小指标。 | 不写入正文、提示词、响应、认证头、完整 URL 或 API Key。 |
| F4-03 | 实现价格与预算偏好。 | 价格表为用户可编辑元数据；本地模型显示 N/A；日/周阈值只提示。 | 未知价格不虚构成本；超阈值不自动停用模型或切换默认模型。 |
| F4-04 | 扩展洞察 API/UI。 | 时间范围、错误分布、延迟分位/均值、成功率、解释性推荐与数据缺失状态。 | 推荐仅说明理由，不改变偏好；所有数据仅当前用户可见。 |

### 阶段 5：扩展/MCP 的显式健康检查

插件/MCP 保持 P2，只有在前述控制面稳定后才进入实现。其重点是可见性与最小权限，而不是后台自动加载。

| 编号 | 任务 | 实现要点 | 验收标准 |
|---|---|---|---|
| F5-01 | 设计健康检查契约与限流。 | 对 Plugin/MCP 按用户显式点击触发，记录非敏感状态、时间、版本、能力摘要与错误分类。 | 打开页面不检查健康；高频重复点击被限流；错误不泄露密钥/连接串。 |
| F5-02 | 配置档影响预览。 | 显示启用项、工具 allowlist、权限变化和被引用的 Agent 定义。 | 应用配置前明确影响范围；不会隐式启动/安装/挂载扩展。 |
| F5-03 | 实现受控动作。 | 启动/停止/挂载/卸载分别要求确认，服务端二次检查 Policy 与引用关系。 | 活跃引用阻止直接卸载；操作均产生审计事件并可在桌面回看。 |

## 5. 验证策略与阶段门槛

当前开发约束为不在本轮计划阶段执行测试、构建、打包或发布。因此下表为**后续用户批准验证后**才执行的门槛，不代表本周期已经通过。

| 验证层 | 最小覆盖 | 阻塞问题 |
|---|---|---|
| 数据/迁移 | 新库创建、旧库升级、历史数据保留、回滚策略说明。 | 表缺失、升级删除数据、跨用户可读写。 |
| API/服务 | 计划状态机、重启恢复、并发、集合过滤、红线字段脱敏、指标幂等。 | 意外创建 Run、越权访问、范围过滤失效、指标记录正文。 |
| Runtime | Chat/Agent 在集合绑定下的来源正确性；指标写入失败隔离。 | 调用结果被指标异常影响；跨集合或跨用户引用。 |
| PySide6 | 三语言切换、空/加载/错误状态、确认框、后台 Worker。 | 主线程阻塞、硬编码混合文案、破坏操作无确认。 |
| 发行 | CI、依赖审计、跨平台构建/签名/安装 smoke。 | 任一正式 `v0.1.2` 门槛缺失。 |

## 6. 风险、缓解与人工确认点

| 风险 | 影响 | 缓解策略 | 是否需人工确认 |
|---|---|---|---|
| 本地应用未运行时无法触发计划 | 用户可能预期 24/7 运行。 | 在 UI 和文档中明确本地执行模型；如需常驻执行，另行评估独立服务方案。 | 是：是否需要应用关闭后继续运行。 |
| 计划恢复错误导致补跑 | 可能创建意外 Agent Run。 | 默认 `misfire_policy=skip`，恢复只推进 next run 并写审计。 | 否，保守默认固定。 |
| 集合过滤遗漏下游查询 | 可能造成范围越界。 | 在服务/查询层强制过滤，逐层传递 binding，不依赖 UI。 | 否。 |
| 指标采集成为隐私泄露面 | 内容或密钥进入遥测。 | 只保存计数、时延、错误类别和用户确认的价格元数据；写入前统一字段白名单。 | 否。 |
| 签名凭据提前接入开发流程 | 增加密钥泄露和发布误触发风险。 | 仅保留变量名称预检与受保护 Environment 文档；不读、不显、不存凭据。 | 是：准备签名 Runner 时。 |

## 7. 里程碑与完成判定

| 里程碑 | 依赖完成 | 进入条件 | 退出条件 |
|---|---|---|---|
| M1：安全数据基线 | F0 | 确认迁移策略与字段白名单。 | 所有新增工作区 API 有服务端 owner 检查与统一脱敏。 |
| M2：可信自动化 | F1 | M1 完成。 | 可解释的恢复/暂停/失败/并发行为；默认无补跑。 |
| M3：受限知识执行 | F2 | M1 完成。 | Chat/Agent 在集合范围内检索且引用可追溯。 |
| M4：可审阅桌面控制面 | F3、F4 | M2/M3 的 schema 稳定。 | Agent 工作台与洞察/控制中心三语言可用，不自动执行。 |
| M5：扩展治理 | F5 | M4 完成。 | 健康检查与扩展动作均显式、可预览、可审计。 |

## 8. 推荐执行顺序

开发应依次完成 `F0 → F1 → F2 → F3 → F4 → F5`。其中 `F0` 是权限、迁移和隐私底座；`F1` 防止自动化在恢复时产生意外执行；`F2` 让已经允许用户保存的集合范围真正成为检索约束。`F3` 和 `F4` 再将定义、模型路由和可观察性组织为一致的桌面体验。最后的 `F5` 只在控制面稳定后扩展至插件/MCP，避免先引入高风险操作。

除非用户明确改变当前约束，实施期间不自动创建 Agent Run、启用计划、发起真实模型请求、下载模型、启动训练、执行构建、签名、打包或发布。正式 `v0.1.2` 仍须满足跨平台签名、安装验证和人工批准门槛。[2]
