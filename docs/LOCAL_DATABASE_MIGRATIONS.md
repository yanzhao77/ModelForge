# 本地 SQLite 增量迁移策略

ModelForge 当前使用 SQLAlchemy `Base.metadata.create_all()` 创建首次运行所需的表，并在启动时执行**仅追加**的 SQLite 迁移。每个已执行迁移版本会写入 `schema_migrations` 账本；该机制适用于本地优先的单用户开发版本，不会删除表、重命名列、回写历史 Agent 定义或修改已有 Run 数据。

## 迁移规则

| 情形 | 处理方式 | 数据安全要求 |
|---|---|---|
| 新表 | 由 `create_all()` 创建。 | 必须包含 `user_id` 或受现有用户对象所有权约束。 |
| 已有表新增列 | 按顺序执行具名迁移；通过 `PRAGMA table_info` 确认缺失后执行 `ALTER TABLE ... ADD COLUMN`，并写入迁移账本。 | 新列必须允许空值或具有安全默认值；重复启动不得重复修改 schema。 |
| 删除/重命名/类型收窄 | 不在自动迁移中执行。 | 单独设计迁移、备份、回滚与人工确认。 |
| 索引 | 新库索引由 `create_all()` 创建；历史库的复杂索引变更必须使用具名版本迁移。 | 不得阻塞现有数据库的启动路径。 |

应用启动先创建缺失表，再应用尚未记录在账本中的具名迁移。缺失表、只读数据库或数据库损坏不应被静默伪装为“迁移成功”：调用方必须保留明确的启动诊断。迁移错误会中止当前启动路径，避免把未知 schema 当作已升级。

## SQLite 并发基线

本地引擎会为每个 SQLite 连接配置有限 `busy_timeout`、`foreign_keys=ON` 和默认启用的 WAL 模式；连接参数可以通过 `DATABASE_BUSY_TIMEOUT_MS` 与 `DATABASE_ENABLE_WAL` 调整。该配置只降低本地读写冲突，不提供分布式锁、无限重试或跨主机协调。所有写入服务仍应保持短事务、幂等语义和可诊断的锁冲突错误。

## 开发与发行门槛

每个涉及持久化模型变更的功能切片都应记录：迁移版本、新表/列、默认值、旧库行为、升级后的用户隔离检查和回滚方式。进入验证阶段前，应分别在全新库和含历史 Agent/Run/Knowledge 数据的副本上执行启动与行为验证。当前开发轮不执行该验证、构建或发布。
