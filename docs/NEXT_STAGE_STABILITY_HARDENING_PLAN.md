# ModelForge 下一阶段稳定性加固计划

**基线提交：** `c92ae0a77ad7e7b9fcabc46f6556c14b0b3047cd`
**适用范围：** FastAPI、SQLAlchemy/SQLite 运行时与 PySide6 桌面客户端。
**工作性质：** 本文定义后续可静态开发的顺序与边界；它不授权运行测试、启动服务、执行迁移、调用模型、创建 Run、运行计划、加载插件、构建、签名、创建标签、推送或发布。

## 1. 阶段目标

上一阶段已经收敛了控制面契约、只读生命周期预览、桌面请求编排、快照治理和发行材料，但仍存在三类影响后续验证可信度的工程债务。第一类是**状态变更与审计记录的事务边界**：部分服务内部自行提交，再由 API 层追加审计，无法保证二者同一事务完成。第二类是**遗留对话路径的用户隔离与统一安全契约**：3.x 运行时已具备策略后备检查和多智能体护栏，而 2.1 AgentEngine 仍维护以名称索引的内存对话状态。第三类是**可诊断性闭环**：已有 `OperationAudit`、runtime/lifecycle diagnostics 与预览 token，但缺少统一的只读审计查询、请求关联传播和验证前的证据映射。[1] [2]

> **主目标：** 在不扩大运行性行为的前提下，让每个控制面状态改变具有可追溯事务边界，让遗留兼容路径具有用户隔离设计，并让管理员能够只读审阅安全脱敏的治理事实。

## 当前静态实施状态

SH1–SH5 的代码、客户端接口和工程材料已按本文顺序写入工作区，尚未运行任何验证。SH1 对计划草稿、模型默认、计划启用、暂停和删除采用单次持久化提交与提交后运行时协调；“立即运行”继续是需要显式确认的独立执行命令，未被错误地包装为普通状态变更。所有 `runtime_sync=pending` 结果都表示需要后续受控协调或验证，**不表示** Agent Run 已创建、计划已恢复或操作已完全验证。

| 成果编号 | 目标 | 可见结果 | 非目标 |
|---|---|---|---|
| SH1 | 控制面原子性 | 状态改变与审计在同一提交单元内成功或回滚。 | 不自动启用、运行或恢复计划。 |
| SH2 | 审计可读性 | 管理员可按用户、动作、对象和关联标识读取脱敏操作摘要。 | 不导出正文、密钥、token 或完整请求。 |
| SH3 | 遗留对话隔离 | 2.1 对话状态按用户和 Agent 隔离，并具备迁移/兼容说明。 | 不发起真实模型或工具调用。 |
| SH4 | 运行时契约一致性 | 工具上下文携带实际权限摘要，事件持久化失败可在只读诊断中观察。 | 不改变已批准的 policy 决策或执行语义。 |
| SH5 | 验证准备 | 固定 SHA 的验证清单能映射到每项加固工作。 | 不运行验证、构建、签名或 Release。 |

## 2. 不变量与安全边界

所有 API Key、Bearer token、密码、证书、私钥、完整模型输入/输出、知识正文和请求正文继续禁止进入审计、诊断、预览、指标、快照、文档示例或 UI。控制面改造必须保留已有成功字段，并以 additive 的 `correlation_id`、`problem.code` 或摘要字段扩展兼容性。

状态变更仍要求既有用户意图与确认边界。特别地，生命周期预览和确认检查必须保持纯只读：不得 `record_operation`、不得 `commit()`、不得清理 retention、恢复计划、补偿插件或处理运行时关闭。正式 tag、开发 tag、推送、构建、签名和 Release 均不属于本阶段工作。

## 3. 顺序化工作包

| 顺序 | 工作包 | 依赖 | 主要交付物 | 允许操作 | 明确禁止 |
|---:|---|---|---|---|---|
| SH1 | 控制面事务与审计边界 | 现有 `ScheduleService`、`ModelReadinessService`、`OperationAudit` | 可选 `commit`/事务协调契约，API 层单次提交，失败回滚语义说明。 | 代码重构、静态审阅。 | 实际计划状态改变、模型调用。 |
| SH2 | 脱敏审计读取与关联传播 | SH1 | 用户/管理员范围的只读审计列表、严格字段白名单、客户端读取方法、控制中心只读入口。 | 只读查询和 UI 展示。 | 审计正文导出、敏感 metadata 回显。 |
| SH3 | 兼容对话用户隔离设计与最小实现 | SH1 | AgentEngine 按 `(user_id, agent_name)` 隔离的内存键、API 传递用户上下文、兼容策略文档。 | 静态代码迁移与接口适配。 | 真实对话、工具调用、历史导入。 |
| SH4 | 运行时策略上下文与事件诊断 | SH2 | 工具上下文权限摘要、事件写失败/队列溢出只读指标和健康解释。 | 只读诊断扩展、数据结构收敛。 | 改变 policy allow/deny、自动恢复事件。 |
| SH5 | 验证映射与文档治理 | SH1–SH4 | 固定 SHA 证据映射、兼容矩阵、历史计划修订与待办收口。 | 模板、schema、静态扫描。 | pytest、Ruff、迁移、构建、签名、标签、发布。 |

### SH1：控制面事务与审计边界

`ScheduleService` 与模型默认偏好服务已为对应控制面公开内部 `commit=False` 契约，使 API 层可以在同一 SQLAlchemy session 中执行“领域变更 → `record_operation()` → 单次 `commit()`”。发生异常时会 `rollback()`，且响应不会表示操作成功。对于涉及内存调度器的启用、暂停和删除，持久期望状态与审计先提交，再进行显式运行时协调；详细边界见 `SCHEDULE_LIFECYCLE_TRANSACTION_STRATEGY.md`。仅修改实现结构，不调用任何状态端点。

兼容策略应保持服务的直接调用者可以显式选择原有提交行为；对 API 控制面则统一关闭内部提交。应先盘点所有调用方，再逐步迁移，不以大范围重写替代局部兼容适配。

### SH2：脱敏审计读取与关联传播

新增只读审计查询时，响应应只包含 `id`、`created_at`、`user_id`（仅管理员范围）、`action`、`object_type`、`object_id`、`correlation_id` 及经 `redact_data()` 再处理的有限 metadata 摘要。查询参数仅支持限制数量、时间窗口、动作和关联标识；不支持自由 SQL、全文正文查询或未分页导出。

桌面端只应在控制中心展示摘要、筛选条件和关联标识，不显示 token、请求载荷或模型正文。API 客户端应集中生成并传递 `X-Request-ID`，将同一用户动作的客户端请求、稳定响应和审计条目关联起来。

### SH3：遗留对话用户隔离

`AgentEngine` 目前以 Agent 名称作为进程内字典键保存对话消息。应设计并实施用户范围键，例如 `(user_id, agent_name)`，并令 API 层在 legacy chat/create/list/delete 调用中显式传递当前用户 ID。为兼容不传用户 ID 的内部调用，可使用明确的匿名兼容 scope；不得将匿名 scope 与真实用户 scope 混合。

这一工作包不把 LangGraph chat 自动迁移为 3.x Run，也不执行任何对话。其成功定义是：代码层面不再以单一 Agent 名称共享真实用户的消息列表，且策略 guard 的现有后备检查不被回退。

### SH4：运行时策略上下文与事件诊断

当前工具执行器已经在执行前进行 policy 后备检查。下一步仅收敛契约：`ToolExecutionContext.permissions` 应由实际 tool/policy 决策派生，使工具能够看到被授予的能力摘要，而不是空列表。对 EventBus 的写失败和队列溢出，扩展现有 runtime diagnostics 的内容无关计数与最近错误类别；不得重放、删除或补偿事件。

该工作包不改变任何 `allowed_tools`、网络、shell、文件系统或人工审批的决策。对进行中工具的取消、插件 scope 生命周期和跨进程调度属于后续获得验证授权后的独立设计项。

### SH5：验证映射与文档治理

建立本阶段工作包到 H7/I6 gate 的映射，明确固定候选 SHA、验证环境、执行人、脱敏证据引用和 No-Go 条件。修订历史计划时必须保留事实与时间边界，不得将“代码已写入”写成“已验证通过”。

## 4. 依赖、风险与确认点

| 风险 | 缓解 | 是否需要用户确认 |
|---|---|---|
| 服务内部提交重构影响直接调用方 | 先提供兼容签名，再逐个将 API 调用方迁移为单次提交。 | 否；不得执行状态操作。 |
| 审计读取泄露 metadata | 字段白名单、二次 redaction、固定分页上限与无正文规则。 | 否。 |
| 用户隔离改造影响遗留会话 | 采用显式 user scope 与匿名兼容 scope；不迁移既有内存状态。 | 否；不得执行 chat。 |
| policy 上下文改动改变执行权限 | 只传递摘要，不更改 `Policy.check_tool()` 的 allow/deny 结果。 | 否。 |
| 文档被误用为发行批准 | 默认 No-Go，模板全部以 `TBD`/`not_run` 表示。 | 是；任何验证或发行需单独授权。 |

## 5. 后续验证门槛

以下是未来授权后才可执行的验证项，本阶段不运行：控制面 mutation 的原子提交/回滚、审计所有权和脱敏、legacy chat 跨用户隔离、`X-Request-ID` 关联、工具权限上下文、EventBus 写失败诊断、PySide6 三语言/关闭路径、旧 SQLite 升级、并发 Run/计划操作和平台签名安装。

默认决策保持 **No-Go**。在固定候选 SHA、当前证据和用户明确批准之前，不得创建新 tag、修改 `APP_VERSION`、推送、签名、上传资产或创建 Release。
