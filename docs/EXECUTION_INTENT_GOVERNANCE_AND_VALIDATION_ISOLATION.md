## 验证前置条件

在任何行为验证之前，发行负责人必须依次完成下表所列前置条件。任何一项缺失均为 No-Go，不能通过“静态审阅通过”例外处理。

| 顺序 | 必要条件 | 允许产生的证据 | 明确禁止 |
|---:|---|---|---|
| 1 | 工作区人工审阅、提交并固定唯一完整候选 SHA。 | 已提交 SHA、差异审阅记录。 | 使用短 SHA、浮动分支或未提交工作区作为候选。 |
| 2 | 获得用户对测试/实际控制面验证的明确授权。 | 授权范围、环境与时间记录。 | 默认触发 Run、训练、provider、插件、计划或迁移。 |
| 3 | 使用隔离测试账户、脱敏数据和已批准目标。 | 请求计数、稳定状态码、关联标识、审计头字段。 | 输入、prompt、模型输出、工具参数、路径、token、API key 或原始异常。 |
| 4 | 按 EI5 映射收集确认、范围、重复请求、关闭回收和三语言呈现证据。 | 受控截图、脱敏日志摘要、状态版本。 | 未授权的真实 provider 调用、跨用户探测或持久化破坏性操作。 |
| 5 | 执行跨平台安装、签名与发行门槛审阅，并取得明确发行批准。 | 平台构建/签名/安装证据、审批记录。 | 创建、移动或替换正式 tag，上传 Release 资产。 |

## 发行 No-Go

下列任一情况存在时，正式标签、签名、资产上传和 GitHub Release 必须保持阻断：未确认请求触发状态变化；跨用户可见或可变更目标；审计、事件、日志、UI、导出或文档出现正文或凭据；候选 SHA 不固定；三语言混用或显示原始异常；审计持久化语义未经验证；未完成跨平台安装/签名证据；或者没有用户或发行负责人的明确批准。

> **审计与运行性边界：** Agent runtime、任务发布器、训练服务、插件管理器和 MCP 连接可拥有独立状态或内部提交。审计失败回执仅表示协调持久化状态未知，绝不表示操作未发生、已回滚或可安全重放。验证必须先进行只读状态核对，再由获得授权的人员决定下一步。
