# ModelForge 下一阶段优化与开发计划

**状态：草案，待产品确认。**

## 1. 目标与当前判断

下一阶段应继续以 **PySide6 桌面客户端** 为交付中心，而不是扩展现有 Web 原型。当前主分支已具备认证、会话、模型、数据集、训练、知识库、智能体、任务中心和运行时页面；本地模型与 OpenAI 兼容远程模型也已统一收敛至“模型”工作区。[1] 当前的 CI 已覆盖 Ruff、依赖审计、后端测试、Docker 构建和健康检查，但真实 GPU、真实 AI 推理/训练及跨平台安装包仍需要特定硬件、网络或签名凭据才能完成验证。[2] [3]

本阶段的核心不是继续堆叠模块，而是将现有能力变成可被首次用户稳定理解、配置、运行、验证和更新的完整桌面体验。优先顺序遵循“**真实可用性 → 发布可信度 → 平台覆盖 → 高级能力**”。

## 2. 基线与主要缺口

| 维度 | 当前基线 | 下一阶段缺口 | 影响 |
|---|---|---|---|
| 桌面工作区 | 已有概览、对话、模型、数据集、训练、知识库、智能体、任务、运行时与设置页面 | 首次使用者缺乏连贯的“配置模型—创建智能体—执行任务—查看结果”引导 | 用户可能在没有可用模型时进入空白工作区 |
| 远程模型 | 支持加密保存 API Key、Responses API 与 Chat Completions API | 缺少面向常用兼容服务的预设、连通性诊断和明确的失败恢复体验 | 接入错误时定位成本偏高 |
| 自动化质量 | CI 已覆盖静态检查、依赖审计、后端测试与 Docker 健康检查 | 桌面端没有独立量化覆盖率门槛；真实远程模型、CPU AI 与 GPU 路径尚未形成可复现证据 | 真实运行时兼容性仍依赖人工验证 |
| 发布工程 | 已生成 macOS `0.1.1-beta.1` 测试资产，并具备 SHA-256 校验与更新机制 | GitHub 尚无 Release；当前构建为 ad-hoc 签名，未完成 Developer ID 签名、公证及 Windows/Linux 分发 | 不宜宣称为生产级跨平台发行版 |
| 文档 | README、架构、API、发布和 QA 文档齐备 | 多处历史测试数量和状态未随最新基线更新 | 对外状态可能产生理解偏差 |

## 3. 建议实施路线

| 阶段 | 优先级 | 交付主题 | 主要工作 | 完成标准 |
|---|---|---|---|---|
| A | P0 | 发布基线与文档校准 | 同步 README、技术报告、QA 报告中的测试数量与版本状态；创建 `v0.1.1-beta.1` GitHub Pre-release 并上传 ZIP、校验文件和测试说明；补充已知限制 | Release 资产与校验文件可下载；客户端检查更新可发现测试版；全部文档指向同一基线 |
| B | P0 | 首次使用与模型可用性 | 增加首次启动向导：连接本地 Ollama 或配置远程服务、验证模型、设为默认模型；无可用模型时为聊天和智能体提供可恢复空状态 | 新用户可在不阅读源码的情况下完成一次远程或本地对话；错误可指出缺失模型、认证失败或协议不匹配 |
| C | P1 | 智能体创建与运行闭环 | 将示例升级为可克隆的 Agent 模板；增加创建向导、工具/权限摘要、审批策略预览、运行前检查与结果回放入口 | 从模板创建 Agent、选择可用模型、发起 Run、审批工具调用并导出任务日志的端到端流程有自动化回归 |
| D | P1 | 远程模型可靠性 | 为 OpenAI 兼容提供商增加预设、`/v1/models` 探测、Responses/Chat 协议回退建议、超时/限流/认证错误的可读诊断；补齐服务层及流式 SSE 集成测试 | 两种协议、流式中断、401/429/5xx、无效模型和密钥不回显场景都有测试与可理解 UI 反馈 |
| E | P1 | 质量门禁与可复现性 | 将桌面端单元测试和离屏 GUI smoke 设为独立 CI job；生成明确的后端/客户端覆盖率报告；为 AI 依赖锁定已验证版本并记录兼容矩阵 | PR 能分别判断后端、桌面端和容器失败原因；依赖重装可复现；安全审计持续执行 |
| F | P2 | 真实 AI 与硬件验证 | 增加固定 revision 的小型 CPU 推理 smoke、最小 LoRA/训练 smoke；接入带 `self-hosted`、`linux`、`nvidia-gpu` 标签的 NVIDIA Runner 并记录 CUDA/驱动/Torch 矩阵 | CPU AI smoke 在受控环境稳定通过；GPU Smoke 不再永久排队，并能验证 `nvidia-smi` 与 GPU 测试标记 |
| G | P2 | 跨平台发布 | 增加 Windows、Linux 打包配置与安装后 smoke；在获得 Apple Developer 证书后完成 macOS Developer ID 签名和公证 | 每个平台至少有可安装测试包；支持平台、签名状态和限制在 Release 中明确标示 |

## 4. 推荐的第一个开发迭代

建议立即实施 **阶段 B 与阶段 C 的最小可用切片**，同时将阶段 A 的文档校准作为发布前置工作。原因是现有用户反馈已表明，智能体在没有本地模型或预建 Agent 时会呈现为空白；这比新增更多后台能力更直接影响桌面端是否“可用”。

该迭代应先建立统一的 `ModelReadiness` 状态：客户端从本地运行时、远程提供商与默认模型配置汇总为“可立即使用、需要配置、连接失败、权限不足”四类状态。聊天页、智能体页和模型页共同使用该状态，不各自实现判断逻辑。随后实现非破坏性的首次使用向导与 Agent 创建向导；用户确认前不得创建 Agent Run、下载模型或开始训练。

| 迭代项 | 涉及模块 | 验收场景 |
|---|---|---|
| 模型就绪状态 | `models_page.py`、`chat_page.py`、`agent_page.py`、API client | 没有模型时显示配置入口；远程模型验证成功后刷新为可用；密钥不在任一界面回显 |
| 引导式配置 | `workspace_page.py`、`provider_dialog.py`、翻译资源 | 简体中文默认，英文/日文切换后没有混合文案；连接失败可定位 URL、密钥、模型名或协议 |
| Agent 创建向导 | `agent_page.py`、后端 Agent API、策略/工具组件 | 模板可复制；模型、工具、权限和审批需求在提交前可审阅；无权限操作被禁用并解释原因 |
| 回归验证 | PySide6 离屏测试、API 集成测试、SSE 测试 | 完成“配置远程模型→流式聊天→创建 Agent→审批→完成 Run→导出日志”流程，且无主线程阻塞 |

## 5. 质量与发布门槛

每个开发切片应满足以下门槛：Ruff、`pip-audit`、全量后端测试、桌面离屏 smoke 和 Docker `/healthz` 均需通过；涉及流式任务或远程模型的改动还需覆盖 SSE 断线重连、认证失效与错误边界。桌面端 UI 测试应继续使用离屏环境，避免将真实 GUI 可见性误当成自动化质量。

`v0.1.1-beta.1` 的 GitHub Pre-release 可以在阶段 A 完成后发布，但必须明确标记为 **macOS arm64 测试版**，并在 Release Notes 中说明未完成的签名/公证、GPU 运行器和跨平台发行验证。不得将当前 ad-hoc 签名包装为正式公证安装包。

## 6. 需要产品确认的决策

| 决策 | 推荐选项 | 影响 |
|---|---|---|
| 下一迭代目标 | 先做首次使用引导与 Agent 创建向导 | 最快提升桌面端实际可用性 |
| 远程服务范围 | 继续以 OpenAI 兼容接口为唯一核心协议，新增预设而不增加独立 Anthropic/Gemini 协议 | 控制维护复杂度并遵守现有架构约束 |
| 测试版发布 | 在文档校准后发布 `v0.1.1-beta.1` Pre-release | 需要在 GitHub 上传现有资产；正式签名/公证可放至后续版本 |
| GPU 验证 | 提供或接入自托管 NVIDIA Runner | 当前 GPU Smoke 已触发但持续排队，无法以 CPU Runner 替代真实 CUDA 验证 |
| 支持平台 | 先固化 macOS arm64，再启动 Windows/Linux 打包矩阵 | 避免在 Beta 期间承诺尚无安装验证的平台 |
