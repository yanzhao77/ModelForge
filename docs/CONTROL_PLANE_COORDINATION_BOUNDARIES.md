# 控制面审计与运行性协调边界

**代码单一事实来源：** `backend/app/core/control_plane_coordination.py`。该目录是 CP3 的静态分类与审阅工具，不开事务、不发布任务、不启动进程、不加载插件，也不连接 MCP/provider。

## 设计原则

控制面回执必须精确表达可知事实，而不是补全无法观察到的跨资源结果。审计行和领域记录若使用同一数据库会话，可共同提交；这只能说明**持久化边界**，不能说明运行时、子进程、发布器或外部连接同时成功。独立运行性副作用一旦发生，即使随后的审计提交失败，也不得声称动作没有发生、已经回滚或可以安全重放。

| 协调类别 | 适用动作 | 可使用的成功回执 | 不确定时回执 | 重放规则 |
|---|---|---|---|---|
| `same_session_persistence` | Memory、Workspace、集合与配置档的同会话变更。 | `persisted`：仅表示领域记录与审计在同一会话内提交成功。 | `durability_unknown` | 先由授权的只读查询核实状态；不得盲目重试。 |
| `post_commit_dispatch` | Agent Run 与 Task 的意图记录、取消、审批、重试及后续发布。 | `accepted`：持久化意图被接受，后续调度仍需独立观察。 | `durability_unknown` | 不得基于不确定回执重复投递；应等待安全状态核实。 |
| `independent_runtime_side_effect` | 训练、插件生命周期、MCP 连接及模型注册。 | `accepted`：请求进入受控路径，不代表子进程/运行时/外部状态已完成。 | `durability_unknown` | 绝不自动重放；先验证副作用与审计状态。 |
| `read_only` | 执行意图预览、预算摘要。 | `read_only`：仅表示读取完成；不代表任何状态改变。 | 不适用 | 读取本身不能作为执行授权或令牌。 |

## 路由改造顺序

后续端点改造必须先完成纯输入/确认/所有权/审计字段预校验，再确定边界类别。对于同会话持久化，领域更新与 `record_control_plane_operation()` 在单一 `commit_control_plane_audit()` 边界内完成。对于提交后调度，先提交用户意图和审计，随后由独立发布器处理；API 回执最多为 `accepted` 或 `pending`。对于独立运行性副作用，不得在调用前后增加伪原子包装；若持久化协调失败，返回既有 `*_AUDIT_DURABILITY_UNKNOWN` 稳定码。

> **禁止表述：** 不得将 `accepted` 表述为已执行、已完成或已回滚；不得将 `durability_unknown` 表述为安全重试；不得在错误、审计、事件、日志或 UI 中加入输入、prompt、模型输出、工具参数、路径、endpoint、token、API key 或原始异常。

## 验证隔离

CP3 没有运行训练、任务发布器、Agent runtime、插件、MCP 或 provider，也没有创建审计测试记录。未来验证需先固定完整候选 SHA、获取明确授权，并以脱敏的持久化状态、请求计数和关联标识为最小证据。涉及训练内部多次提交、运行时内存状态和外部进程的场景必须单独判定，不能因本目录存在而视为原子或幂等。
